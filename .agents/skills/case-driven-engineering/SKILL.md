# 案例驱动的工程选题与落地

目标：把“想做一个东西”推进为有现实案例支撑、可检验、可回退的项目决定。先弄清别人做出了什么及其边界，再决定复用和改进哪一部分。不要用术语和完整架构代替工程证据。

本技能适用于不同工程项目；[案例与工程复盘](references/casebook.md)中 2026-10-07 的智能车讨论是历史示例。每次应用时先读取当前任务和项目现行真源，不从该示例继承项目目标、预算、期限或硬件状态。

## 使用入口

- 选题或重新选方向：从步骤 1 开始，使用 [案例与工程复盘](references/casebook.md) 的作品索引寻找线索，再联网核验相关原作者资料。
- 已选方向、需要实施计划：保留已确认目标，从步骤 3 的复现差异开始，不重新展开所有方向。
- 距离方案讨论只剩一两天：完成步骤 1—4 的纸面判断，按 [一页决策单](references/decision-sheet.md) 输出可讨论结果。硬件未装好不妨碍形成附带验证条件的方案。
- 用户纠正方向或现实约束：更新受到影响的判断，明确上一结论撤销或保留的原因。用户重新开放选题时，不把旧文档中的方向继续当成确定需求。

这是工作顺序，不要求每轮把七步全部讲一遍。续谈时先说当前在哪一步、这次要解决哪个决定，结束时记录判断、证据、未知和下一动作。对简单问题直接回答，不启动整套流程。

## 七步工作流程

### 1. 确定这次要做的决定

从现有上下文提取：最近一次交付、最终成品交付、长期目标；已有硬件；新增预算；人手与经验；平时测试条件；用户明确的偏好。分别记录用户确认、资料确认和待验证事项。

遇到预算、期限、场地等硬边界，先核对能快速排除方案的条件。例如比较购买与自制时，先查同等配置的当前价格和已有投入的增量成本，再决定是否值得深查结构与接口。

用一句话写当前问题，例如“明天拿哪两个项目候选和老师比较”，不要擅自替换成“先把车组起来”。缺信息时先做不依赖该信息的工作；只问会改变方向的关键问题。

产出：简短约束卡。通过条件：知道这次判断需要支持哪一个决定。

### 2. 先建立作品候选，再研究算法

广泛选题时，先展示若干种不同的成品行为，通常覆盖至少三类任务，避免只是同一方案换名称。用户已限定范围时在该范围内检索。优先作者项目主页、竞赛队技术报告、大学课程作品、GitHub 的文档与问题记录；视频和评论用于发现线索及复现障碍。

每个案例先回答：谁做了什么；结果是遥控、脚本、闭环自主还是仿真；在什么场景成功；用了哪些现成基础；公开了什么；有什么未完成或失败。暂不钻进具体算法。

拿到与决定有关的证据后收敛，通常只深查 2—3 个候选。不要用几十个链接掩盖判断缺失。

产出：作品对比表和原始来源。通过条件：候选有实际作品证据，能解释为什么进入或退出比较。

### 3. 比较“别人已跑通的系统”与“我们的条件”

逐项比较机械/运动方式、执行器与接口、传感器视角、算力与运行环境、场景与人工辅助、工具和加工能力、复现资料及测试条件。

检查完整复现包：BOM 与具体版本、装配/接线资料、代码、依赖/权重、标定与训练数据、运行及测试说明、许可。缺项不自动淘汰，但要明确我们需要补什么。只公开代码或有大量 stars 不能证明实物可复现。

标明哪些可以照用、哪些只借鉴方法、哪些必须重做。不要把换主控、换运动结构、换相机视角视为“简单微调”。涉及购买时先按相同配置查增量成本，再分析值不值；注明时间、地区、是否含电控/组装/运费/工具，历史 BOM 不当作当前报价。

产出：复现差异与成本表，列出最可能影响成败的少数未知。通过条件：有可说明的复用依据，或明确知道缺哪项证据。

### 4. 先验证最可能推翻方案的假设

按“失败后影响多大、目前多不确定、怎样最低成本获知”选第一项试验。不能机械地总先装配，也不能因为软件方便就只写软件。

例如：手持相机取景检查看不看得到目标；借原工程测试设备协议；用实际尺寸检查机械可达范围；拿一段实录验证感知；原版仿真检查几何可行性。仿真只回答其模型能覆盖的问题，不能替代摩擦、间隙、光照和实际安装测试。

试验写清输入、成功/失败标准、时间/花费上限和失败后的替代方案。时限前做不了实测，标记为待验证假设并给出首个验证安排，仍然交出可讨论方案。

产出：主选、备选及关键验证卡。通过条件：最大风险已有证据，或其影响与退路已明确。

### 5. 跑通一个完整的最小任务

优先运行最近似案例的原始基线，记录版本和配置；硬件不同则做必要适配。尽早让“输入—决策—执行—反馈/结果”连起来。遥控、人工提供目标、离线数据可以分阶段使用，但必须标出被人工或模拟替代的环节。

沿一个可演示任务推进，勿同时重写底层库、换整套框架和增加多个陌生能力。接口至少明确单位、数据新鲜度、所有权、失败响应。保留日志/录像、配置、可回退版本以及必要的人工接管。

产出：可运行基线及复现方法。通过条件：关键任务可重复执行，知道失败发生在哪里，而非只看到机器人在动。

### 6. 对照基线改进并整体验证

每次改动围绕一个明确收益：成功率、精度、适应范围、成本、调试时间等。根据问题选择局部测试、离线回放、仿真、实物全链路测试，避免把所有验证都推到末尾。

按预先定义的场景记录尝试总数、成功/失败、人工干预、耗时和版本。单模块更快不代表整机更好；需要同时看整体延迟、负载和任务结果。测试环境变化要落到具体变量，如光照、目标位置、地面、负载。

调试超过约定预算且没有新增信息时，留下假设、试验、结果和下一种区分办法，先恢复可用基线。不要无区别重复尝试，也不要把降级结果伪装成原目标完成。

产出：改进前后证据及仍未解决的问题。通过条件：能证明改进有效并说明适用范围。

### 7. 留出交付和复盘阶段

冻结可演示版本，记录启动、标定、复位、异常恢复和已知限制。保留连续过程证据，区分作者声明、自己跑过、实物多次测试及跨条件验证。

复盘记录：原假设、观察、原因已确认/仍未知、以后何时复用这条经验。经验要带条件，不能把一个项目的权宜方案变成所有项目的规定。

产出：稳定演示、可重现说明和少量可复用经验。只有某项自动化已节省重复劳动时再扩成工具平台，不为“工程化”先造大平台。

## 证据与讨论约束

- 区分作者实测报告、构建指南、路线建议和我们的实测。引用定位到章节、页码、提交或问题记录；没看过视频就不声称已经看过。
- 作者复盘不一定正确；根因猜测保持为猜测。评论中的抱怨是调查线索，不自动等同通病。
- 阅读代码、生成代码、编译通过、仿真通过、实物通过各自证明的事情不同。
- 开源许可与真实硬件假设都属于复用条件。不能从差速小车推定阿克曼能原地转向，也不能从高位俯拍方案推定低位前视相机可直接使用。
- 在不知道用户目标时给出比较依据；已经有足够依据时给出带理由的推荐，不把研究和选择重新全部推给用户。
- 若用户明确扩大选题范围，先扩展案例样本。不要仍把所有道路导向旧选题。
- 默认中文。优先让用户看到当前结论、案例证据与下一动作，详细证据放链接后的参考文件。
- 本技能授权的是分析流程；不额外授权购买、发布、联系他人、改写主工程或启动实体设备。

## 自检

交付前检查：是否回答当前决定；是否有结果与失败证据；是否说明案例差异；第一项试验能否改变决定；是否给了可运行基线的来源；是否把新增复杂度计入工期；是否保留下一动作与判断状态。
