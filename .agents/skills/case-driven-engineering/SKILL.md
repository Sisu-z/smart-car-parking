# 技术工程化落地判断（案例驱动）

本技能帮助判断“一个技术目标怎样做成可重复验证的结果”，不是替用户选一个新项目。案例是证据与可复用资产的入口，不是要求每次都列一张选题排行榜。先遵守当前任务的目标、授权和项目真源；历史讨论不能覆盖新决定。

## 何时使用

- 目标未定：比较实际做成的任务、日常测试条件与复现代价，再建议选什么。
- 目标已定：不重开选题；判断用什么现成基础、先验证哪个假设、最小闭环怎样跑通。
- 实现卡住或准备交付：检查证据、接口、测试覆盖和返工原因，决定继续、降级、回退或换路线。

简单问题直接回答。只分析当前会改变决定的环节，不要求每次机械执行全部流程。

## 四个核心判断

1. **现实中能否反复测试。**把“能做”落到场地、设备、时间、人手、成本和验收环境；问日常多久能获得一次有效反馈。一次演示成功不等于具备稳定迭代条件。来源示例：[C01 Cornell Segway](references/casebook.md)。
2. **什么基础可复用，何时能试完整任务。**先看已有作品实际完成了什么，区分自主、遥控、脚本、仿真及人工辅助；检查版本、接口、结构、视角、数据、许可和复现材料。能复用的直接用，必须适配的列出工作量；尽早接通输入→处理/决策→执行→结果反馈。来源示例：[C02 FRC 254](references/casebook.md)。
3. **创新是否是解决瓶颈的最小改动。**从机械、传感、控制、算法、交互、测试工具中选真正影响任务结果的一处；保留可比较的原始基线。不要默认“创新”必须是更复杂的算法。来源示例：[C05 SO-101 / LeRobot](references/casebook.md)。
4. **失败是否转化为下一次判断的证据。**先测最可能推翻路线的假设；集成时核对真实环境和系统负载；保留失败记录、可回退版本与适用边界。成熟团队也会误判，关键是能据证据修正。来源示例：[C09 NUbots](references/casebook.md)。

这些是从案例归纳出的判断原则，不声称所有工程师都遵守同一套固定流程。[案例与工程复盘](references/casebook.md)仅在需要找先例或核对上述案例时阅读；其中的历史价格、版本和作者计划不是当前事实。

## 从当前问题走到下一步

1. **定义要判断的事。**用一句话写当前目标与可观察验收；区分用户已确认条件、资料事实、设计假设和未知。记录预算、期限、已有资产、日常测试环境及最终使用环境。若目标已确定，不自行替换目标。
2. **找少量最接近的已完成先例。**优先原作者仓库、构建指南、测试报告、问题记录和复盘；只深查足以影响当前取舍的案例。核对作者到底做成了什么，不把愿景、演示视频或高 star 数当成完整复现证据。没有合适先例就说明缺口，转向小试验，不编造“成熟方案”。
3. **拆复用与适配。**按“可直接复用 / 需适配 / 只借鉴思路 / 不宜复用”标出部件、代码和方法。只检查与本次判断相关的机械与电源、传感视角、运行环境、接口、依赖/数据、标定、测试条件和许可；变更关键前提时重新评估成本和风险。
4. **先证伪最大风险。**选失败后最可能推翻路线、又能低成本获得证据的假设。试验应有输入、环境、通过/失败标准、时间或成本上限及失败后的分支。仿真、编译、离线回放和实物测试各有证明范围，不能互相冒充。
5. **建立最小全链路基线。**尽量先运行原版或小幅适配的现成实现；记录版本、配置、人工代替环节、日志和复现步骤。一个模块能跑不等于完整任务达标。先保证安全与可回退，再做增量改进。
6. **逐项改进并交付。**每次改动声明预期收益，用相同或明确变化的测试条件比较前后结果；记录失败、人工干预、整体延迟/负载与边界。交付时冻结可复现版本，写明操作步骤、已验证范围和未解决问题。调试反复没有新信息时保存证据并回到基线，改用能区分假设的试验。

步骤可以跳过、并行或回退；顺序由任务依赖和最大未知决定，不默认先装硬件、先写软件或先搭大平台。需要正式记录路线取舍时使用[技术落地判断卡](references/decision-sheet.md)，不强制为日常小问题填表。

## 输出与边界

默认先给：**当前判断、依据、最关键未知、下一项低成本验证、失败时的退路**。涉及采购或开源复用时补充同配置增量成本、版本和许可；价格与兼容性应按当前来源重核。涉及实测时明确“阅读过 / 编译过 / 仿真过 / 实物单次 / 实物多次”各自的证据等级。作者的根因猜测仍是猜测。

本技能只提供判断方法，不额外授权购买、发布、联系他人、改写主工程或启动实体设备。默认中文；若项目有现行文档或安全约束，以它们和本次用户要求为准。
