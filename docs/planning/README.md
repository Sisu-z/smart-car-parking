# 初步可行计划书：专业材料与接手入口

本目录是总体计划的证据附录，不是第二套项目说明或派工台账。当前唯一总体方案是 [00_project_master_plan.md](../../00_project_master_plan.md)，正式分配、修订、run_id 和状态只在 [GitHub Issues](https://github.com/Sisu-z/smart-car-parking/issues) 维护。

## 计划书应回答什么

不是只列“OpenCV / PI / Reeds–Shepp”名字。对每个能力说明：真实输入与输出/单位；数据从哪里来；可复用实现及固定版本/许可；项目需适配什么；实现步骤和前置条件；如何离线/台架/实车验证；失败后如何定位和停止；费用/空间/机械/供电假设如何影响选择。不给无证据的厘米级或成功率承诺；年底交付按参考阶段窗口和测试轮次安排，不固定到哪天几点。

主线：两线道路循迹与曲线转弯 → 观察普通车位线并自主找位 → 在线倒库 → 按指令出库。绕障后置。随机起点/朝向、跨场地仍是目标，工作范围/起始域需确认，不悄悄换成固定发车和已知车位。

## 依赖怎样交接

1. 专业窗口先查本仓库实物/代码证据，再比较少量最贴近的原作者案例。研究者需明确案例实做范围和与本车的差异，不把开源 README 的目标等同独立复现。
2. 电气审核给出可允许的供电/外设条件；底层控制可先做代码差距与测试计划，实际通电/烧录不在本轮新增授权内。
3. 机械给尺寸、转向/视野的测量方法与条件范围；算法可据参数区间做敏感性分析，不在实测前宣布某张地图或相机组合够用。
4. 系统与算法可并行核输入/输出和运行时需求。双方的接口只能提案；总监收敛后更新 INTERFACE_CONTRACTS，再允许消费者按版本实现。
5. 总监审查准确提交/文件后，在上游原 Issue 记录接受范围，通知下游准确版本、可用输入、失效假设和仍需等待的决定。下游回填采用版本及需重算项。

## 约束与停止规则

已确认的库存/空间/预算看 PROJECT_CONTEXT 最新补充，真正开放问题看 OPEN_QUESTIONS。会导致采购、地图定制、不可逆加工、接口冻结或目标改变的现实缺口，先由总监集中问用户；缺回答时相关结论为候选，但独立项继续。

用户在专业聊天提出新要求时，专业窗口记录原意和影响、提交总监判断，不自行广播为全项目新标准。共享中央文件只由总监整合，专业窗口交接写自己的产物及原 Issue/PR。

先用现有测试、VOFA+、OpenCV、固定 PythonRobotics 和回放工具；不先搭新大平台。重复失败最多三次有依据尝试，无新证据则记录后换独立项；安全门槛保持。

团队指南固定版 [v0.3.0](https://github.com/Sisu-z/project-team-playbook/blob/v0.3.0/START_HERE.md)；执行者读取其 SKILL、executor/shared-work，审查整合读取 review-integrate。在线任务可直接读取固定版本；需要离线接手时先取得同版完整副本，不能仅靠链接声称离线可用。
